# Lite 1.1 gap analysis and decision record

Reviewed 11 September 2026. The result is a new PRD and matching companions. Existing PRDs, application source, Claude session and Software Factory records were not modified.

## Evidence and limits

The review used the original Lite 1.0 PRD and its two detail companions/expression vectors, the local Claude session titled **Software Factory Smart Form MCP setup**, persisted Software Factory work-order contexts/plans/review logs, and the current local `softwareFactory` implementation. Its account/authentication, platform/tenant administration, authorization roles, database migrations, canonical package, rule corpus, README, Compose configuration and Angular package were inspected. Local source and relevant input hashes are recorded in `source-evidence.json`.

The Claude session contains the user's six-part confirmed decision message on 10 September: username/password, no public signup, two administration tiers, temporary-password and invitation onboarding, no-email operation, password changes/recovery and first-admin provisioning. Later session/review records document the user's explicit package contract stamp and 64-bit/BigInt decisions. These sources establish product intent; an assistant's historical claim of completed tests does not establish current product acceptance.

The visible session and persisted records were readable. This review did not have a live Software Factory connector, did not independently verify pending/accepted suggestion state and did not change any remote requirement, blueprint or work order. The local implementation directory was not a Git checkout when inspected, so no commit/branch provenance is asserted. Source hashes identify the inspected inputs. No services, browser product flows or product test suite were run for this documentation revision. Historical test totals are deliberately not presented as new verification.

The implementation is a partial foundation: real server authentication/provisioning code and a canonical model/rule evaluator exist. The client remains a scaffold in the inspected files; invitations, self-service password recovery, the complete builder/respondent UI and other retained product areas cannot be inferred complete from backend work-order review. Work-order review state is not full Lite acceptance.

## Scope preservation

All 80 Lite 1.0 numbered requirements remain in the new PRD; the disposition register records unchanged/rewritten rows and additions. Original Core removals remain exclusions and IDs are not recycled. No other retained field, authoring, form-versioning, preview, localization, attachment, public sharing, same-device save/resume, response-read/export, outbound-webhook, audit/retention or extension requirement is dropped because the current implementation is incomplete.

The prior reductions remain: no SSO; no inbound machine-client credentials; public respondents only; repeat/identical submissions allowed; no cross-device resume exchange; no personalized prefill launch; no live remote choices; no named-helper workflow; no custom domains; no completion/error analytics dashboard; no response correction/revision/assignment/follow-up/notes/tags/status workflow; no actor/code-exchange administration screen; no per-form export grant; no saved scenario catalog; compact Play/Pause and Click to Ask only, without answer dictation or typed questions. Staff invitation links remain; they are not respondent invitations. Form-draft/release history remains; it is not response revision workflow.

## New defaults versus confirmed scope

Confirmed scope comes from the user's messages: authentication and the two admin tiers, both onboarding paths, email-independent use, password lifecycle, initial administrators, chosen stack/UI, explicit semantic stamp and exact 64-bit integers. The following are documented design defaults chosen in this revision, rather than misattributed user instructions: exact credential/session lifetimes, password minimum/capacity, uniform integer-string public transport and profile 4.0.0, shared-account reset boundary, explicit pending first-owner state and protected recovery runbook. They can be changed through a versioned decision applied consistently across docs/contracts/tests.

No additional authentication methods, second factor, account self-signup, enterprise federation, device management or response workflow is introduced. The new details make normal password login and the requested user management usable and testable.

## Remaining delivery obligations

The PRD is a specification, not a generated full application contract. Complete JSON Schemas/OpenAPI, full canonical packages, executable server/browser adapters, all translated fixtures, fault/load generators and the independent acceptance ledger remain implementation/evaluation deliverables. This revision supplies normative prose, updated expression vectors and coverage checks; it does not label all schemas or product tests complete. Current Software Factory suggestions must be checked in that tool before reusing its plans; no remote record synchronization is claimed here.
